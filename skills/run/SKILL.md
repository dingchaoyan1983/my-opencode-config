# Run

Execute the Tasks defined in a task plan document generated by the `plan` skill, applying code changes in order and verifying them.

**Input**: The plan file path or file name. If empty, prefer the **most recently generated or referenced plan file in the current conversation**. If no plan file has appeared in the conversation, use `list_dir` to read the current project's `.agents/plan/` directory and `question` toolto let the user choose from its `.md` files. If the directory does not exist or is empty, tell the user to generate a plan with the `plan` skill first, then stop.

Do not continue until the plan file to execute is identified.

---

## Workflow

### 1. Locate the plan file

Parse the input in this order:

- Absolute path -> use it directly.
- Relative path -> resolve it relative to the current project root.
- File name only, such as `2026-07-24-admin-start-prod.md` or `2026-07-24-admin-start-prod` -> look under `.agents/plan/` and append `.md` automatically.
- Empty -> prefer the **most recently generated or referenced plan file in the current conversation**. If no plan file has appeared in the conversation, use `list_dir` to read `.agents/plan/` and `question` tool to let the user choose a plan file. If the directory does not exist or is empty, tell the user to generate a plan with the `plan` skill first, then stop.

Stop and notify the user if locating the file fails.

### 2. Read and parse the plan

Use `read_file` to read the complete plan file and identify:

- `# Title`: The overall task goal; reference only, do not modify.
- `## Current State`: Background information; reference only, do not modify.
- `## Task N: <description>`: The list of tasks to execute, in ascending N order.

Parse the following from each Task section:

- Text instructions: what the task does and which files to reference.
- Code blocks with language tags such as \`\`\`js / \`\`\`json / \`\`\`tsx: file contents to create or write.
- Parameter-source lists (`- \`parameter-name\` -- source`): important configuration to verify against source files during execution.

### 3. Execute each Task

Use `manage_todo_list` to track all Task progress. Execute each Task in order:

1. **Announce**: Output the number and description of the Task currently being executed.
2. **Explore reference files in parallel**: If the Task mentions comparison or reference terms such as "refer to", "compare with", "similar", or "same as", first read those reference files in parallel with `read_file` to understand existing patterns and conventions.
3. **Apply changes**:
   - Before modifying an existing file, reread it with `read_file` to confirm its current content.
   - To create a new file, use `create_file` and use the plan's code-block content directly.
   - To modify an existing file, use `replace_string_in_file` or `insert_edit_into_file` for an exact replacement.
   - Independent file creations/modifications may be started in parallel in one message.
4. **Verify parameter sources**: Check every source file listed under "parameter sources" and confirm that its value matches the plan. If a mismatch is found, use `question` tool (yes/no) to ask, "The parameter source value differs from the plan. Ignore the mismatch and continue?" Continue for "yes" and stop for "no".
5. **Verify code changes**:
   - First determine whether the Task is documentation-only. If it has no fenced code blocks with language tags and contains only Markdown instructions, skip verification and mark it "documentation-only; verification skipped".
   - For code changes:
     - Check the project's `package.json` scripts and `AGENTS.md` to determine the available TypeScript type-check command.
     - **Default**: Run only the TypeScript type check. Prefer an existing typecheck script; otherwise run `npx tsc --noEmit` directly.
     - **When explicitly requested**: If the user explicitly requests lint, build, or broader verification, run the requested scope.
     - Follow any verification steps explicitly specified in the plan, such as starting a service or visiting a URL.
     - If verification fails, stop, report the error, and do not continue to later Tasks.

### 4. Summarize

After all Tasks are complete, output a summary:

- The executed Task list and each result (success / failure / skipped).
- The status of verification commands.
- If every Task succeeded with no failures or skips, use `run_in_terminal` to delete the executed plan file: `rm ".agents/plan/<file-name>"`.
- Tell the user to commit the changes manually if they want to keep them; the `run` skill does not commit automatically.

---

## Format Constraints

1. **Follow the plan exactly**: Do not add, remove, or rewrite Tasks without authorization; do not do work outside the plan.
2. **Write code content verbatim**: Code blocks in the plan are the final file contents; do not add comments, reformat, or optimize them.
3. **Always verify parameter sources**: Reread the source files and confirm every parameter listed in the plan.
4. **Verify every Task**: Run verification after each Task involving code changes; documentation-only plans may skip verification.
5. **Stop on failure**: If any Task or verification fails, stop immediately, report the problem, and wait for the user's decision.
6. **Do not commit to Git automatically**: `run` only applies code changes and performs verification; it does not run `git add` or `git commit` unless explicitly requested.

---

## Behavioral Guidelines

- Read the complete plan before execution and understand the dependencies between Tasks.
- Read reference files in parallel for efficiency when the plan mentions multiple comparison files.
- Prefer verification commands already defined in the project's `package.json` scripts.
- If the plan does not match the actual code, such as an incorrect path or changed function signature, stop and ask the user to update the plan.
- Preserve the project's existing code style, including indentation, naming, and quotation marks.
